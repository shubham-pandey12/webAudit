1. Introduction

React makes it easy to start building a user interface. You create a component, add some state, fetch data, and render the result. In the beginning, everything feels simple.

Now imagine building a business dashboard. It starts with a few pages. A few months later, it includes authentication, user management, analytics, notifications, filters, data tables, and several API integrations.

Suddenly, the code becomes harder to manage. A single component might handle API requests, validation, filtering, loading states, and rendering. Similar buttons and cards are implemented differently across pages. A small change in one feature unexpectedly breaks another.

The problem is not necessarily React itself. The problem is how we organize the application as it grows.

Scalable React architecture is about making future changes easier without adding unnecessary complexity today.

In this article, we will build a practical approach to structuring React applications using TypeScript. We will cover reusable components, custom hooks, feature-based architecture, API services, state management, testing, and common mistakes.

What you will learn
  • How to organize a growing React project.
  • How to separate UI, data fetching, and business logic.
  • How to choose between local, shared, server, and URL state.
  • How to test features and avoid premature abstractions.

2. What Does Scalability Mean in Frontend Development?

In frontend development, scalability is not only about handling more users. It also means that the application can grow without becoming unnecessarily difficult to understand, test, or modify.

A scalable React application should make it easier to add features without rewriting unrelated features, reuse UI without duplicating behavior, test logic independently, and let multiple developers work on separate parts of the product.

Consider two implementations of a product list. One puts fetching, filtering, error handling, and rendering in one component. The other separates the page, data-fetching hook, API module, and UI components. Both can show the same screen, but the second structure often becomes easier to maintain as requirements grow.

That does not mean every component needs its own file or every function needs a custom hook. Architecture should solve real problems, not create more files for the sake of organization.

3. The Problems with an Unstructured React Application

Here is a common implementation. It is acceptable for a small demonstration, but it combines several responsibilities in one component.

App.tsx
import { useEffect, useState } from "react";

type Product = {
  id: number;
  name: string;
  price: number;
};

export default function App() {
  const [products, setProducts] = useState<Product[]>([]);
  const [search, setSearch] = useState("");
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState("");

  useEffect(() => {
    async function loadProducts() {
      setLoading(true);
      try {
        const response = await fetch("/api/products");
        if (!response.ok) throw new Error("Request failed");
        const data: Product[] = await response.json();
        setProducts(data);
      } catch {
        setError("Unable to load products");
      } finally {
        setLoading(false);
      }
    }
    loadProducts();
  }, []);

  const filtered = products.filter((product) =>
    product.name.toLowerCase().includes(search.toLowerCase())
  );

  return (
    <main>
      <h1>Products</h1>
      <input value={search}
        onChange={(event) => setSearch(event.target.value)}
        placeholder="Search products" />
      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}
      <ul>
        {filtered.map((product) => (
          <li key={product.id}>
            {product.name} - ${product.price}
          </li>
        ))}
      </ul>
    </main>
  );
}
When does this become a problem?

When requirements add pagination, sorting, product details, retry behavior, and another page that needs the same product data. The component gains responsibilities, API logic is harder to reuse, and isolated tests become more awkward.

Do not refactor only because a component has reached a certain line count. Look for responsibilities that change independently and separate them when doing so improves clarity.

4. The Core Principles of Scalable React Architecture

4.1 Separation of concerns

Each part of the application should have a clear responsibility. A page coordinates the screen; a UI component displays information; a hook shares stateful behavior; an API module communicates with the backend; and a utility handles a small operation.

4.2 Reusability

Shared components help keep behavior consistent. But two components that look similar do not always need to be merged. If they serve different purposes or are likely to evolve differently, separate implementations may be easier to maintain.

4.3 High cohesion and low coupling

High cohesion means related code stays together. Low coupling means one part of the application does not depend unnecessarily on another part's internal details. A product feature, for example, should not need to know how authentication tokens are stored internally.

4.4 Explicit data flow

Data should move through clear boundaries. A page obtains the data it needs, passes values to child components, and responds to user actions through explicit callbacks. Avoid hidden dependencies and excessive global state when local state or a function argument is enough.

5. Choosing a Folder Structure That Can Grow

A type-based structure is a reasonable starting point:

src/
├── components/
├── hooks/
├── pages/
├── services/
├── types/
└── utils/

As the application grows, each folder can fill with files from many unrelated features. Finding everything related to products might require searching through components, hooks, services, and types separately.

For a medium-sized application, a feature-based structure with a small shared layer is often easier to navigate.

src/
├── app/
│   ├── App.tsx
│   ├── router.tsx
│   └── providers.tsx
├── components/
│   ├── ui/
│   │   ├── Button.tsx
│   │   ├── Input.tsx
│   │   └── Spinner.tsx
│   └── layout/
│       ├── AppLayout.tsx
│       └── Sidebar.tsx
├── features/
│   ├── products/
│   │   ├── api/productsApi.ts
│   │   ├── components/
│   │   │   ├── ProductList.tsx
│   │   │   └── ProductCard.tsx
│   │   ├── hooks/useProducts.ts
│   │   ├── pages/ProductsPage.tsx
│   │   ├── types/product.types.ts
│   │   └── utils/filterProducts.ts
│   └── users/
│       ├── api/
│       ├── components/
│       ├── hooks/
│       ├── pages/
│       └── types/
├── lib/http.ts
├── hooks/
├── utils/
└── main.tsx
LocationResponsibility
app/Application setup, routing, providers.
components/ui/Generic UI components shared across features.
components/layout/Shared layouts and navigation.
features/products/Product-specific UI, logic, API, and types.
lib/Shared infrastructure, such as an HTTP client.
hooks/ and utils/Only genuinely shared hooks and utilities.
Practical rule

Organize code around the business features developers work on, not only around the technical file types they create. Keep feature-specific code together and share functionality when it is genuinely common.

6. Building the Application Step by Step

Step 1: Define the data types

Create features/products/types/product.types.ts.

export type Product = {
  id: number;
  name: string;
  price: number;
  category: string;
};

TypeScript helps catch mistakes during development and documents the shape of data used by components and API functions. But TypeScript types do not validate external JSON at runtime. Validate untrusted API data when appropriate.

Step 2: Move API communication into a module

Create features/products/api/productsApi.ts.

import type { Product } from "../types/product.types";

export async function getProducts(
  signal?: AbortSignal
): Promise<Product[]> {
  const response = await fetch("/api/products", { signal });

  if (!response.ok) {
    throw new Error("Unable to fetch products");
  }

  return (await response.json()) as Product[];
}

The page no longer needs to know the details of the HTTP request. If the endpoint changes, there is one clear place to update it. The type assertion does not validate the server response; use runtime schema validation or a suitably typed API client if stronger guarantees are needed.

Step 3: Separate data-fetching behavior

For a small app, fetching with useEffect can be enough. When several components need the same query or you need caching, background refetching, retries, and request deduplication, a server-state library such as TanStack Query can reduce custom code.

Install it if the project does not already use it:

npm install @tanstack/react-query

Create features/products/hooks/useProducts.ts.

import { useQuery } from "@tanstack/react-query";
import { getProducts } from "../api/productsApi";

export function useProducts() {
  return useQuery({
    queryKey: ["products"],
    queryFn: ({ signal }) => getProducts(signal),
  });
}

The query key identifies the cached data. If the result depends on a category or search parameter, include that parameter in the key. Configure a QueryClientProvider near the application root and create the QueryClient once rather than on every render.

import {
  QueryClient,
  QueryClientProvider,
} from "@tanstack/react-query";

const queryClient = new QueryClient();

export function Providers({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <QueryClientProvider client={queryClient}>
      {children}
    </QueryClientProvider>
  );
}

Step 4: Extract a reusable UI component

Create features/products/components/ProductCard.tsx.

import type { Product } from "../types/product.types";

type ProductCardProps = {
  product: Product;
  onSelect?: (product: Product) => void;
};

export function ProductCard({
  product,
  onSelect,
}: ProductCardProps) {
  return (
    <article className="product-card">
      <h2>{product.name}</h2>
      <p>Category: {product.category}</p>
      <p>${product.price.toFixed(2)}</p>
      {onSelect && (
        <button onClick={() => onSelect(product)}>
          View details
        </button>
      )}
    </article>
  );
}

The component receives a product through props. It does not fetch data, know about routing, or maintain a second copy of the product list. The callback lets a parent respond to selection.

Step 5: Create the product list

Create features/products/components/ProductList.tsx.

import type { Product } from "../types/product.types";
import { ProductCard } from "./ProductCard";

type ProductListProps = {
  products: Product[];
  onSelectProduct: (product: Product) => void;
};

export function ProductList({
  products,
  onSelectProduct,
}: ProductListProps) {
  if (products.length === 0) {
    return <p>No products found.</p>;
  }

  return (
    <div className="product-grid">
      {products.map((product) => (
        <ProductCard
          key={product.id}
          product={product}
          onSelect={onSelectProduct}
        />
      ))}
    </div>
  );
}

The list has one responsibility: display a collection of products. It does not need to know where the data came from. The stable key helps React identify list items when the list changes.

Step 6: Extract filtering logic

Create features/products/utils/filterProducts.ts.

import type { Product } from "../types/product.types";

export function filterProducts(
  products: Product[],
  search: string
): Product[] {
  const normalizedSearch = search.trim().toLowerCase();

  if (!normalizedSearch) return products;

  return products.filter((product) =>
    product.name.toLowerCase().includes(normalizedSearch)
  );
}

This is a pure function: the same inputs produce the same result, and the original array is not modified. We can test empty searches, mixed letter casing, and unmatched results without rendering React.

Step 7: Compose the page

Create features/products/pages/ProductsPage.tsx.

import { useMemo, useState } from "react";
import { ProductList } from "../components/ProductList";
import { useProducts } from "../hooks/useProducts";
import { filterProducts } from "../utils/filterProducts";
import type { Product } from "../types/product.types";

export function ProductsPage() {
  const [search, setSearch] = useState("");
  const [selectedProduct, setSelectedProduct] =
    useState<Product | null>(null);

  const {
    data: products = [],
    isPending,
    isError,
    error,
    refetch,
  } = useProducts();

  const filteredProducts = useMemo(
    () => filterProducts(products, search),
    [products, search]
  );

  if (isPending) return <p>Loading products...</p>;

  if (isError) {
    return (
      <section>
        <p role="alert">
          {error.message || "Unable to load products."}
        </p>
        <button onClick={() => refetch()}>Try again</button>
      </section>
    );
  }

  return (
    <main>
      <h1>Products</h1>
      <label htmlFor="product-search">Search products</label>
      <input
        id="product-search"
        value={search}
        onChange={(event) => setSearch(event.target.value)}
        placeholder="Enter a product name"
      />
      <ProductList
        products={filteredProducts}
        onSelectProduct={setSelectedProduct}
      />
      {selectedProduct && (
        <aside aria-live="polite">
          Selected: {selectedProduct.name}
          <button onClick={() => setSelectedProduct(null)}>
            Clear selection
          </button>
        </aside>
      )}
    </main>
  );
}

The page coordinates the screen. It owns the search term and selected product, reads server data through the hook, and passes values to the list.

Do we need useMemo here?

Not always. For a small product list, calculating the filtered result directly may be simpler. Memoization is useful when the calculation is expensive or referential stability matters to downstream consumers. Avoid adding it by default.

7. Understanding the Architecture

We now have several files, each with a clear responsibility. The important point is not the number of files; it is how responsibilities are separated.

ProductsPage→useProducts→productsApi→Backend API

The response is managed by the query cache and exposed to the page.

ProductsPage→ProductList→ProductCard
  • API changes can be handled in the API module.
  • Query behavior can be managed through the data-fetching hook.
  • UI changes can be made to the list or card without rewriting the API.
  • Filtering can be tested as a pure function.
  • The page remains responsible for coordinating the screen.

The diagram represents logical flow, not every internal detail of TanStack Query. As the feature grows, add boundaries based on real requirements rather than predicting every possible future need.

8. Understanding State Management

Not all state belongs in the same place. Classifying state by its purpose helps avoid unnecessary complexity.

Local UI state

Examples include an open dropdown, selected tab, temporary form input, or tooltip visibility. Use useState when state is local to a component or a small part of the tree.

Shared client state

Examples include a multi-step workflow, a complex editor, or preferences used by distant components. Start with props and local state. Use Context or a state library when sharing requirements justify it. Redux Toolkit can help when client state has complex update rules, multiple consumers, or a need for explicit transitions and debugging.

Server state

Products, profiles, orders, and analytics data can become stale or change on the server. Server state involves caching, refetching, loading, errors, and synchronization. TanStack Query can handle many of these concerns.

URL state

Search terms, pagination, sorting, and filters may belong in the URL if users should be able to bookmark, share, or refresh the page without losing them.

The goal is not to choose one state-management tool for everything. Choose the simplest appropriate location for each kind of state.

9. Designing a Maintainable API Layer

As an application grows, features may need shared API behavior such as authentication headers, timeouts, request identifiers, and common error handling. A shared HTTP client can centralize behavior when the requirements justify it.

export async function request<T>(
  url: string,
  init?: RequestInit
): Promise<T> {
  const response = await fetch(url, init);

  if (!response.ok) {
    throw new Error(
      `Request failed with status ${response.status}`
    );
  }

  return response.json() as Promise<T>;
}

A feature can use it like this:

import { request } from "../../../lib/http";
import type { Product } from "../types/product.types";

export function getProducts(): Promise<Product[]> {
  return request<Product[]>("/api/products");
}

This is a starting point, not a complete production HTTP client. The generic type does not validate server JSON, and the helper does not standardize error types, timeouts, or authentication. Design the API layer around actual needs rather than building a large abstraction too early.

10. Reusable Components Without Overengineering

Suppose two buttons share the same visual design and behavior. A shared button component makes sense. But a product card and a user profile card do not automatically need to become one generic card just because both contain an image, title, and text.

Extract stable UI patterns when doing so improves consistency. Avoid giving every component dozens of configuration props before real use cases require them.

type ButtonProps = {
  children: React.ReactNode;
  disabled?: boolean;
  onClick?: () => void;
};

export function Button({
  children,
  disabled = false,
  onClick,
}: ButtonProps) {
  return (
    <button
      type="button"
      disabled={disabled}
      onClick={onClick}
    >
      {children}
    </button>
  );
}

A production button should also consider focus indicators, keyboard interaction, visual variants, loading states, and accessibility.

Remember

Good abstraction removes duplication and clarifies intent. Bad abstraction hides simple behavior behind unnecessary complexity.

11. Routing and Code Splitting

A growing application may have product, user, analytics, and settings pages. Loading every page's code at the beginning can increase the initial JavaScript bundle. Code splitting allows parts of the application to load when needed.

import { lazy, Suspense } from "react";
import { createBrowserRouter } from "react-router-dom";

const ProductsPage = lazy(
  () => import("../features/products/pages/ProductsPage")
);

export const router = createBrowserRouter([
  {
    path: "/products",
    element: (
      <Suspense fallback={<p>Loading page...</p>}>
        <ProductsPage />
      </Suspense>
    ),
  },
]);

This is a simplified route configuration. A complete app also needs its router provider, layouts, error boundaries, and missing-route handling. Lazy loading is not automatically beneficial for every small component. Use production build analysis and browser measurements to decide where code splitting helps.

12. Testing the Architecture

A maintainable architecture should be easy to test. The boundaries we created give us natural places to test different kinds of behavior.

Unit tests

Test pure functions such as filterProducts with empty searches, matching products, mixed letter casing, and unmatched results.

Component tests

Render ProductCard and verify that the product name and price appear. Check that selecting the product calls the expected callback.

Integration tests

Test the product page with its data-fetching behavior and loading, error, and success states. Mock the network boundary instead of relying on a live backend.

End-to-end tests

Use a browser testing tool such as Playwright to verify a user journey: open the products page, wait for the list, search for a product, and open its details.

These tests answer different questions. A unit test cannot prove the entire user journey works, while end-to-end tests may be too slow for every edge case. Combine focused unit tests, component and integration tests, and a smaller set of high-value end-to-end tests.

13. Common Architecture Mistakes

Creating abstractions too early

Do not build a universal form engine because one page needs a form. Start with the simplest implementation that fits the requirement and extract an abstraction when a clear need appears.

Creating a giant shared components folder

Keep feature-specific components close to their features. The shared layer should contain genuinely shared functionality, not become a storage place for unrelated code.

Using global state for everything

A dropdown's open state usually does not need to live in Redux just because the application uses Redux. Keep local state local unless there is a concrete reason to share it.

Duplicating server data

If a server-state library already manages a product query, maintaining another manually synchronized copy in a global store can introduce stale data and unnecessary complexity. Decide which layer owns each piece of data.

Building giant components and giant hooks

Moving hundreds of lines from a component into one custom hook does not automatically improve architecture. The hook should have a clear responsibility; otherwise, the complexity has only moved to another file.

Ignoring loading and error states

Requests can fail, return empty results, or take longer than expected. Design these states intentionally rather than assuming every request succeeds.

Optimizing without measurements

Memoization, code splitting, and virtualization are useful tools, but they introduce complexity too. Measure the problem before choosing the optimization.

14. A Practical Checklist for New Features

  • Is the feature's code organized in a clear location?
  • Are its data types explicit?
  • Is API communication separated from presentation?
  • Does each component have a clear responsibility?
  • Is state stored in the simplest appropriate place?
  • Are loading, empty, and error states handled?
  • Can important logic be tested independently?
  • Are shared components genuinely reusable?
  • Are accessibility and responsive behavior considered?
  • Are performance decisions based on evidence rather than assumptions?

You do not need to solve every possible future problem before shipping a feature. Use this checklist to catch avoidable complexity and missing behavior.

15. Conclusion

Scalable React development is not about creating the largest folder structure or using every available library. It is about making the code easier to change as requirements grow.

We started with a component that handled API requests, filtering, state, and rendering. We then separated the API module, data-fetching behavior, reusable UI, filtering logic, and page composition. This gives each part a clearer responsibility and creates useful boundaries for testing and future changes.

The best architecture depends on the size and needs of the application. A small project may need only a few components and hooks. A larger application may benefit from feature-based modules, explicit API boundaries, shared infrastructure, and dedicated state-management tools.

Build the simplest architecture that supports today's requirements while making tomorrow's changes easier.

Good architecture should help developers move faster with confidence, not force them to work around layers of unnecessary abstraction.

Further practice
  • Implement the product example in a small React + TypeScript project.
  • Add pagination and sorting, then decide where their state belongs.
  • Write unit tests for filtering and component tests for product selection.
  • Measure the production bundle before and after adding route-level code splitting.
